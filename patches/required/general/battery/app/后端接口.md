# 电池管理 App：系统侧接口说明（给 Linux 那边做 patch）

> 这是 App 作者最初写的需求文档,留作背景。实际实现以 `patches/required/general/herald-apps/README.md`(通道、鉴权、回包写法)和 `parts/006.app/README.md` 为准;
> 和本文不同的地方:读取用一条 `battery overview`;回包是 O_EXCL 新建后 `chown -h` + `chcon -h`(不是先写好再 chown/chmod);`battery info` 已直接带 `soh` / `cycle_count` / `charge_full_uah` / `charge_full_design_uah`。

App：`com.lenovo.tb321fu.battery`（"电池管理"）。它没有桌面图标，只能从 **设置 → 电池 → 电池管理** 进入。
App 只负责界面，所有读写都通过 herald 现有的 `battery` 插件完成。系统侧要做下面四件事。

## 1. 把 APK 放进系统分区

| 项目 | 要求 |
|---|---|
| 位置 | 推荐 `/system_ext/app/TB321FU-Battery/TB321FU-Battery.apk`；放 `/product/app/` 或 `*/priv-app/` 也可以 |
| 权限 | App 不申请任何权限，不需要 privapp-permissions 白名单 |
| 签名 | 自签名（`keystore/tb321fu-battery.jks`），不需要平台签名 |
| 目录权限 | 目录 0755，APK 0644，SELinux 标签 `system_file`（system_ext 下跟随分区默认即可） |

为什么必须放系统分区：设置只把**系统 App** 里带 `com.android.settings.action.IA_SETTINGS` 的 Activity 注入成入口，普通安装的 App 不会出现在设置里。

入口元数据（已写在 App 清单里，系统侧不用改）：

- 分类：`com.android.settings.category.ia.battery`
- 标题：电池管理
- 图标：可着色
- 摘要：由 `content://com.lenovo.tb321fu.battery.summary/getSummary` 动态提供，例如"健康度 95% · 充电上限 80%"

## 2. herald 为这个 App 开一条专用通道

现有的 App 通道只能配对一个前端，而且已经被 OMK 工具箱占用。这个 App 需要**另外一条固定通道**，不需要配对，也不需要 token，和工具箱的配对互不影响。

通道目录：`/data/user/0/com.lenovo.tb321fu.battery/files/`（只服务 user 0 即可）

### 一次请求的流程

| 步骤 | 谁 | 做什么 |
|---|---|---|
| 1 | App | 删除旧的 `herald_resp` |
| 2 | App | 写 `herald_req.tmp`（一行命令加 `\n`，UTF-8），再 rename 成 `herald_req` |
| 3 | herald | **2.5 秒内**把 `herald_req` 拿走（rename 到自己的目录或直接删除），然后执行命令 |
| 4 | herald | 把结果写到 `herald_resp.tmp`，chown 成 App 的 uid:gid、chmod 0600，再 rename 成 `herald_resp` |
| 5 | App | 读取 `herald_resp` 后删除它 |

### 时序要求

| 情况 | App 的行为 |
|---|---|
| `herald_req` 超过 2.5 秒没被拿走 | 认为系统服务不在，撤回请求，界面显示"无法连接系统电池服务" |
| 读命令 6 秒内没有回包 | 超时 |
| 写命令 25 秒内没有回包 | 超时（`bypass on` 要阻塞 4–8 秒，在这个范围内） |

所以 herald 用 inotify 或 ≤500 ms 的轮询看这个目录就够了。App 一次只发一条请求，不会并发。

**注意 rename 的原子性**：`herald_resp` 一定要先写 `.tmp` 再 rename，否则 App 可能读到半个文件。

### 鉴权（代替配对）

- 只服务包名 `com.lenovo.tb321fu.battery`。
- 这个包必须装在系统分区：`pm path` 的结果在 `/system_ext/`、`/product/` 或 `/system/` 下，或者包标志里有 SYSTEM。如果被装成 `/data/app` 的更新包，就拒绝。
- `files/` 目录的 owner uid 要等于这个包的 uid（防止目录被替换）。

### 命令白名单

只接受下面这些命令，整行完全匹配；其他命令一律回 `err not allowed`。

```
^battery info$
^battery (protect|limit|bypass) status$
^battery protect on ([2-9][0-9]|100) ([2-9][0-9]|100)$
^battery protect off$
^battery limit ([2-9][0-9]|100)( ([5-9][0-9]|100))?$
^battery limit off$
^battery bypass (on|off)$
```

参数范围的校验（`protect` 要求 min < max，`bypass on` 要求电量 > 15% 等）沿用插件现有的逻辑。

## 3. 回包格式（沿用现有 battery 插件，不用改）

第一行是 `ok …` 或 `err <原因>`，后面是 `key=value` 行。出错时 App 会把 `err` 后面的原因原样弹给用户看，所以原因最好写中文。

App 用到的 key：

**`battery info`**

- 整机：`level`、`status`（`Charging` / `Discharging` / `Not charging` / `Full`）、`health`、`temp_c`、`voltage_mv`、`current_ma`、`time_to_full_s`、`time_to_empty_s`、`usb_online`、`wireless_online`
- 电芯数量：`cells`、`cycle_max`
- 每块电芯 n：`cell{n}_soh_raw`、`cell{n}_cycle_count_raw`、`cell{n}_temp_raw`（0.1 ℃）、`cell{n}_voltage_raw`（µV）、`cell{n}_current_raw`（µA）、`cell{n}_produce_date_raw`、`cell{n}_activate_date_raw`（YYMMDD）、`cell{n}_manufacturer`

**`battery protect status`**：`protect=on|off`、`min`、`max`

**`battery limit status`**：`limit`（没有这个 key 时 App 会退回去读 `raw` 的后三位）、`recharge_raw`

**`battery bypass status`**：`bypass=on|off`、`charger=yes|no`、`level`

### 建议在 `battery info` 里加四个字段（可选）

加上之后 App 会多显示"满电容量 / 设计容量"，整机健康度也不用再从电芯推算：

| key | 来源 | 当前设备上的值 |
|---|---|---|
| `soh` | `/sys/class/power_supply/battery/soh` | 95 |
| `cycle_count` | `/sys/class/power_supply/battery/cycle_count` | 265 |
| `charge_full_uah` | `/sys/class/power_supply/battery/charge_full` | 5544000 |
| `charge_full_design_uah` | `/sys/class/power_supply/battery/charge_full_design` | 6550000 |

没有这四个字段时，App 的退路是：

- 健康度取各电芯 `soh_raw` 的最小值；
- 循环次数取 `cycle_max`；
- "满电容量"一行不显示。

## 4. 其他

- **重启后的状态**：充电上限和长期插电保护在重启后要不要自动恢复（插件里的 `remembered=`），由系统侧决定。App 每 5 秒读一次状态，系统侧怎么定，界面就怎么显示。
- **换传输方式**：如果系统侧更想用 binder 服务或 socket，App 里只需要换一个类。实现 `Backend` 接口（`exec(String cmd, long timeoutMs)` 返回同样格式的文本），在 `Backends.get()` 里返回它即可。

## 5. 验证方法

先用演示模式确认界面没问题。演示模式不需要系统 patch，数据是写死的样例：

```
adb shell am start -n com.lenovo.tb321fu.battery/.MainActivity --ez demo true
```

接上 patch 之后，按下面顺序检查：

1. 设置 → 电池 里出现"电池管理"入口，摘要会在打开过一次 App 之后变成实际数据。
2. 进入 App，电量、电芯 1/2 和充电开关都有真实数据，不再显示"无法连接系统电池服务"。
3. 打开充电上限，用 `battery limit status` 确认生效；关闭后同样确认。
4. 插着充电器打开旁路充电，几秒后开关保持在打开状态，状态显示"旁路供电中"；拔掉充电器后显示"连接充电器后可开启"。
5. 用 `adb install` 装一个同包名的 `/data/app` 版本，herald 应该拒绝服务它。
